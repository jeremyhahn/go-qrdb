# #1619: nightly clusterproof soak against a 3-node docker cluster

## Objective

The per-PR `test-clusterproof` job only unit-tests the harness. Run the real
proof (`make cluster-proof` soak runner, then `make cluster-proof-check`)
every night against a three-node cluster booted from the release image on
the CI runner, and keep the evidence bundle as an artifact.

10. The healed node then failed pebble WAL replay ("encfs: block
   authentication failed"): ENOSPC tore encfs's in-place rewrite of the
   WAL's trailing block, and every unclean power loss does the same (go-xkms
   #2290). Dropping the bad final block loses acknowledged records, since
   that block was rewritten after an earlier Sync (ruling 913, the #1637
   Codex P1). Ruling 956 fixes the cause: never overwrite bytes a Sync made
   durable. Pebble WALs (*.log) and MANIFESTs (MANIFEST-*) are written in a
   framed, seal-on-sync layout (header flag): each frame carries its
   plaintext length, sealed with its index and length as AEAD additional
   data, and the Write after a Sync starts a new frame. On open a torn,
   short or unauthenticated frame past the durable boundary ends the log
   (it holds no acknowledged byte); a frame inside it that fails
   authentication refuses the open with ErrAuthFailed (see 12). Every other file keeps the fixed-size
   layout (sstables need ReadAt arithmetic). A WAL or MANIFEST in the old
   layout (a device's preserved WAL) records no durable boundary, so a
   final block that is too short or fails authentication refuses the open
   (TrailingBlockTooShortError, ErrAuthFailed) rather than drop records;
   that tear is why the framed layout exists.
   Tests: a power-cut filesystem wrapper (byte-granular tear of the
   in-flight write) over many seeds at file level and through Pebble
   (WAL and MANIFEST cuts, every acknowledged key read back), old-layout
   open, tamper and frame swap refused. The disk-full nemesis expects the
   node to recover with no acknowledged write lost.
11. A power cut inside the header of a fresh WAL or MANIFEST (Pebble makes
   a WAL on every memtable rotation) left a file shorter than its header,
   and the open refused it with ErrTruncatedHeader, blocking boot. The
   header is written before any record and nothing is acknowledged before
   the first Sync, so for WAL and MANIFEST names a header prefix (0 bytes
   up to header length - 1) opens as an empty log; a read-write open writes
   a fresh header over it and zeroes nothing. A prefix counts as a tear
   only when it is shorter than a fresh header for the barrier and its
   header size and wrapped-DEK length fields, where the file reaches them,
   equal that fresh header's (a barrier whose fresh headers differ in size
   refuses). A size field corrupted to a larger in-bounds value also ends
   past EOF, but the file may hold synced records: it refuses and its bytes
   stay (ruling 913). A complete
   header that fails to parse, authenticate or unwrap still refuses, and
   so does a short header on any other file (sstable, OPTIONS). Tests: a
   cut at every byte offset of a fresh WAL and MANIFEST header (both opens
   empty, appends survive a reopen); Pebble cuts during a fresh WAL and
   MANIFEST header write with every acknowledged key read back; a corrupt
   framed header and a short sstable header refused; a WAL and MANIFEST
   with a synced record and a corrupted header size refused by both opens,
   file unchanged.
- Coverage back to the baseline (#1637 verify gate): table-driven unit

12. #1637 Codex round 1: the "final frame" rule in 10 could not tell a
   torn frame from a synced one corrupted later (it zeroed acknowledged

## Soak stall

Evidence (two CI runs of "Soak [clusterproof nemesis]", this head and
c84ed60282de): BOOT-01 passes; 3 nodes, 30m, faults disk-full, kill,
partition-bridge, partition-isolate-leader, partition-majority-minority,
pause. The "ok" count freezes for good (595729 ok at 18m40s after the 10th
fault; 496235 ok at about 8m50s after the 5th) while failed and
indeterminate keep rising about 4/s each to 30m0s: after one point no op
succeeds again, across later heals. Then 3-4 minutes of silence in the
post-duration phase until the runner's shutdown signal (make exit 143, no
verdict, no bundle).

Root cause: not proven from code; nothing is guess-fixed. Suspects, in
order:

- Per-node disk budget. `mount_data` gives each node 1 GiB of ext4
  (`CLUSTERPROOF_DISK_MB`). Both stalls began near 500-600k ok ops although
  they came 10 minutes apart, which points at a cumulative resource, not a
  particular fault: raft log plus pebble data (40% puts, 15% CAS on 64 keys
  with no proven snapshot/compaction in the image's `/etc/qrdb/qrdb.yaml`)
  filling every node's volume at about the same op count would halt all
  three replicas at once, and no heal frees it.
- A heal that leaves its node unusable: `docker start` on a still-running
  node after disk-full (a node that did not exit on ENOSPC keeps a failed
  store), or a partition rule left in a node's netns.
- The workload's redial path keeping a dead connection or stale endpoint
  after a restart (would not explain the cluster-wide freeze alone, since
  liveness fails on every node).
- Runner shutdown during the post phase: memory (writeBundle held the
  ~600k-op history up to five times at once) is a candidate; unproven.
  Since slice 16 writeBundle holds one copy.
- The linearizability check: it runs inside writeBundle and again in
  cluster-proof-check, with `linearizability.DefaultTimeout` (10m) per key
  across GOMAXPROCS keys at once, and porcupine's search over many
  indeterminate writes is a memory/CPU candidate. Since slice 17 a key
  holding more than `DefaultMaxIndeterminate` indeterminate writes is
  refused before any search starts, so the next run must end with a
  verdict and every node's log; the freeze itself stays open.

What the next CI run shows: each fault's inject and heal line ("window N
<nemesis> inject|heal ... [targets]: ok|error"), so the fault at which "ok"
freezes is named; the phase lines (healing, liveness, final read,
replicas, writing bundle) with elapsed stamps, so a stall is attributed to
a phase; and, with the deadline, a verdict and a bundle (with every
node's log) even when the cluster never recovers. If the freeze follows
no particular fault and the node logs show ENOSPC, raise
`CLUSTERPROOF_DISK_MB` or enable snapshots in the rendered node config.

## CI soak at c643ed1875

The 30 min soak ended "invalid under seal none" with two defects:

1. Acknowledged ops froze from the ninth fault on while failed and
   indeterminate kept rising. A timed-out op kept its connection, and a
   session left half-open by kill, pause or partition timed out every later
   op without reporting the connection lost, so clients stayed pinned to
   it. Fix: an indeterminate outcome (or a lost connection) fails the
   client over: drop the connection, dial the next endpoint. A definite
   rejection still keeps it. Test: `TestRunFailsOverFromHalfOpenSessions`
   (half-open fake; phases hang every node but one healed earlier, so the
   run finishes only if clients return to healed nodes).
2. E2 unavailable: 86 indeterminate writes on one of 16 fixed keys, past
   the checker bound of 16. Fix: Jepsen independent keys. Each slot's key
   is retired for a fresh one after `KeyMaxOps` (1000) ops, or when a
   write could take its indeterminate writes (in-flight writes counted)
   past `KeyMaxIndeterminate` (16, the checker bound, unchanged). Tests:
   `TestKeyspaceRetiresAtEachBound`, `TestRunKeepsEveryKeyDecidable` (a
   long history, a third of writes indeterminate: no key over the bound,
   linearizability judges every key),
   `TestDefaultKeyMaxIndeterminateIsTheCheckerBound`.

## fx1637e

Two lane-verify Codex P1s on the soak fixes.

1. The final read ignored the post-run deadline: `opContext` dropped the
   parent deadline with its cancellation, so a stalled final `get` ran a
   whole `OpTimeout` past `PostTimeout`. Fix: an operation ends at the
   earlier of `OpTimeout` and ctx's deadline; a plain cancellation is still
   ignored. Test: `TestRun_PostPhaseDeadline/final_read_stalls` (reads stall
   until their context ends, `OpTimeout` 10m, `PostTimeout` 300ms: the run
   ends, writes the bundle and reports the post-run phase not finished).
2. A timed-out read did not fail the client over: reads classify as `fail`
   and a deadline is no lost connection, so read-only clients kept a
   half-open session. Fix: `unanswered(err)` (deadline, gRPC
   `DeadlineExceeded`, a transport error wrapping a timeout); `finish`
   fails over on it too. Reads stay `fail`; a definite rejection keeps the
   connection. Tests: `TestRunFailsOverFromHalfOpenReads`, `TestUnanswered`.

## Out of scope

- Any change to the schedule cron.
