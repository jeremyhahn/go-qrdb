- The singular `device` resource is kept as the SPEC wrote it, beside
  `devices:onboard`.

  password family's resource:verb form.
- Enforcement is consumer-side: go-qrdb has no password store, so the store
  that owns shared passwords asks the PDP.

## iam1651d

SPEC item (2) authz-claim-roles: an identity's roles come only from the
go-qrdb user record it binds to.

- Change: `finalizeIdentity` (`pkg/auth/middleware/middleware.go`) now clears
  `Roles` up front, beside `RoleBindings` and `Attributes`, so no path keeps
  the roles an authenticator returned. Only a found, active record's
  `RoleIDs` set them. The `Identity.Roles` and `Authenticator` docs in
  `pkg/auth/auth.go` say so.
- Paths closed, all through the one `authenticate()` call every transport
  (REST, gRPC, Unix, QUIC, MCP) shares:
  - Subject with no user record: it used to keep its claimed roles; now it has
    none, so RBAC default-denies it.
  - Node with no user store: same.
  - Sealed tenant: claimed roles were kept; now only the IdentityGated
    surface stays reachable.
  - A capability module's fallback identity (for example a token go-xkms
    minted) claiming Admin: refused unless go-qrdb holds a record granting it.
  - Holder identities were already cleared; the separate clear in that
    branch is gone, because the up-front clear covers it.
- Test fixture: `authtest.FixedAuthenticator.Users()` (`fixed_users.go`) is a
  read-only store holding the record of the identity the authenticator
  currently returns. Every test that relied on a fixed caller's roles now
  pairs `authmw.WithAuthenticator(fa)` with `authmw.WithUserService(fa.Users())`.
  Migrated: 22 test files in `pkg/api` and the SDK (5 `grpctest` helpers,
  which also drive `pkg/api/unix`; `grpc/service_vlog_test.go`; 5 in mcp, 5 in
  quic, 5 in rest; `sdk/go/transport/internal/sotest/sotest.go`) plus 4
  middleware test files. Callers whose tests do not depend on the caller's
  roles (allow-all or deny-all authorizers, `pkg/server`, and the rest files
  `encoded_path_authz`, `handlers_audit_verify_scope`,
  `handlers_delegation_policy`, `module_route_guard`, `role_assignment_wiring`
  and `certs_tenant_scope`) were left alone; their packages pass unchanged.
- Tests: `pkg/auth/middleware/claim_roles_test.go` covers all four
  finalizeIdentity paths, the REST fallback against the real RBAC PDP (403 →
  200 only with a record) and the gRPC/Unix interceptor (PermissionDenied → OK
  only with a record). `pkg/auth/authtest/authtest_test.go` covers the
  fixture store.
- No CLI e2e: a CLI user always authenticates against a node whose user store
  holds their record, so what the CLI sees does not change. The closed paths
  need an authenticator that returns roles (a capability module's fallback or
  a test double), which the CLI cannot inject. The unit tests drive the shared
  `authenticate()` path and both interceptors with the real PDP.
- Not run here: `pkg/sql/mysql` and `pkg/sql/pgsql` build only under the
  `qrdb_mysql` / `qrdb_pgsql` tags, and their driver modules are not in the
  lane's offline module cache (GOPROXY=off). Neither package is edited; CI
  runs them.

Open question for the owner (not implemented):

- `RBACClient.Authorize` / `POST /permissions/authorize` still evaluates the
  `Roles` the caller sends in the wire `Identity`. That is the same claim
  path, one hop out: a client can ask "would these roles allow X" and the
  PDP answers from roles no record grants. Recommendation: resolve the
  subject's roles on the server from its bound user record (the same
  `finalizeIdentity` binding), and drop `Roles` from the wire `Identity`
  outright, with no compat field. A "what-if" evaluation over named roles,
  if it is wanted, would be a separate admin-only call that says so.
