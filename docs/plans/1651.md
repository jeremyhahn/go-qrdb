# Plan: #1651 IAM exposure

## iam1651b: tenant-status list filter

**Decision.** The tenant list takes an optional status filter on every
surface: REST (`?status=`), gRPC and Unix (`TenantListRequest.status`,
replacing `google.protobuf.Empty`), QUIC (`tenant.List` payload), MCP
(`qrdb_tenant_list` `status`), embedded, the Go SDK
(`TenantClient.ListTenants(ctx, *transport.ListTenantsRequest)`, nil lists
all) and the CLI (`qrdb tenant list --status`).

**Semantics.** `tenant.FilterByStatus` holds the rule. Empty is no filter.
`active`, `suspended` or `disabled` keeps only tenants stored with exactly
that status, so a legacy tenant with no stored status matches only the
unfiltered list. Any other value is refused with `*tenant.InvalidStatusError`
naming the allowed statuses (400 / `INVALID_ARGUMENT`).

**Where it runs.** At the API surfaces, after `FilterTenantList`, so the
filter can only narrow what the caller may already see.
`TenantServicer.ListTenants` stays unfiltered for internal callers.

**`deleted` is not a status.** A deleted tenant is a retired-id tombstone,
listed by `ListDeletedTenants` / `qrdb tenant list-deleted`; `--status
deleted` is refused as an invalid status rather than mapped to that list.

**Tests.** `pkg/tenant` `TestFilterByStatus_*`; per-server
`StatusFilter` tests on gRPC, QUIC, REST and MCP; SDK embedded
`TestListTenants_StatusFilter`, REST `TestListTenants_SendsStatusQuery`, MCP
`TestListTenants_SendsStatusArg`; `cmd/qrdb` `TestTenantList_StatusFlagIsSent`;
CLI E2E `TestTenantStatus_CLI_ListStatusFilter_PerProtocol` over REST, gRPC,
QUIC, MCP and Unix.

## iam1651c: Unix peer-credential identity

**Decision.** On Linux the Unix listener reads `SO_PEERCRED` (uid, gid, pid)
from each accepted connection before the TLS handshake, and the gRPC
interceptors bind it into the request context (`auth.WithPeerCredential`).
`unix.peer_credentials` maps a uid, or a primary gid, to a tenant and
username; `auth.PeerCredentialAuthenticator` (method `peercred`) is installed
last in the authentication chain only when a mapping exists.

**Semantics.** A mapping names an account, never a role: the identity is
filled from the stored account and its roles decide through RBAC. A missing
account holds no roles, so every request is denied. An account's
`auth_methods`, when set, must list `peercred`. A uid match wins over a gid
match. An unmapped peer is refused with `peer_credential_unmapped`
(`UNAUTHENTICATED`). A client certificate or consumer authenticator on the
socket decides first. Config validation refuses a mapping with both or
neither of uid and gid, an empty user, and a duplicate uid or gid, even
while `protocols.unix` is off.

**Tests.** `pkg/auth` and `pkg/api/unix` `PeerCred` tests; the wiring and
middleware chain-order tests; `pkg/config` `TestUnixPeerCredentials_*`; CLI
E2E `TestUnixPeerCredential_CLI_BindsMappedUser` (a certificate-less caller
is refused, then admitted once its mapped account holds `operator`, and
still refused `users create`).

**Open owner question.** Should a gid mapping also match the peer's
supplementary groups? `SO_PEERCRED` reports only the primary gid, so today a
gid mapping matches the primary group only; supplementary groups would need
a `/proc/<pid>/status` read, which races a pid reuse. Recommendation: keep
primary gid only. A second question: should a mapping to a system-tenant
account (empty `tenant`) be refused at validation? Recommendation: allow it,
since the account's roles still bound it, but say so in the docs.
