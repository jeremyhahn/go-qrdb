# Plan: #1596 self-hosted Go caches off the runner temp dir

## Objective

On self-hosted pool hosts the Go build and golangci-lint caches move from
`$RUNNER_TEMP/ci-cache` (root filesystem, grew to 168 GB) to a persistent
directory on `/mnt/raid0`; hosted runners keep `$RUNNER_TEMP/ci-cache` with
actions/cache. `scripts/ci-cache-dir.sh` picks the directory.

## Slices

1. (done, bd71a0265) `scripts/ci-cache-dir.sh` + `scripts/ci-cache-dir_test.sh`;
   ci.yml points every stage at it; actions/cache on hosted runners only.
2. Codex round 1 (two P1 findings):
   - Eviction must not delete a directory a concurrent stage has
     bind-mounted. The cache lives in generations,
     `<base>/gen-<UTC stamp>/{gobuild,golangci}`, and `<base>/current` names
     the live one. Each job that selects a generation touches its
     `.last-use` marker. Past `CI_CACHE_MAX_GB` the job creates a new
     generation and switches `current` by atomic rename of a temp file. An
     old generation is deleted only once its marker is older than
     `CI_CACHE_RECLAIM_HOURS` (default 7, longer than the 6 h job limit);
     the current one and the job's own are never deleted. Selection,
     rotation and the reclaim decision run under `flock`; reclaimed
     generations are renamed to `trash-*` and deleted after.
   - Cleanup must remove container-owned (uid 10001) files. A helper,
     `scripts/ci-cache-clean.sh`, empties each directory as root in a `--rm`
     toolchain-image container (`find /c -mindepth 1 -delete`, only
     DAC_OVERRIDE and FOWNER, no network), then removes it with a plain
     `rm`; without docker or an image it is a plain `rm -rf`. A survivor is
     a `::warning::`, never a failed job. ci-cache-dir.sh and ci.yml's six
     "Remove the temp Go caches" steps call it.
   - Tests: rotation over the cap, reclaim only past the age, the current
     generation never deleted, pre-generation dirs by age, the legacy temp
     cache and a stage-owned generation through the helper (read-only dirs
     stand in for uid 10001, a fake `docker` for the container), helper
     failure warns with exit 0, and the real helper on a uid-10001 fixture
     when docker and a local image are available (skipped otherwise).
3. lane-verify Codex review (two P1 findings):
   - Security: stages ran the shared, mutable toolchain tag after
     `ci-image.sh load` verified an ID. `load` now prints the ID and records
     it for the tag in `CI_IMAGE_IDS` (default `$RUNNER_TEMP/ci-image-ids`);
     `in-toolchain-image.sh` runs the recorded ID in every create/run.
   - Reliability: the stage launch's chown walk runs once per generation
     under `flock` on `<gen>/.owner-lock` and writes `<gen>/.owner-ready`;
     a walk ignores ENOENT (concurrent `DiskCache.Trim`), fails otherwise.
   - Tests: ci-image_test (ID printed and recorded); in-toolchain-image_test
     (ID reaches create/run, bad record refused, ENOENT, marker skip).
4. lane-verify Codex P1: the remaining tag consumers. `ci-cache-clean.sh`
   runs the recorded ID (a non-`sha256:` record disables the helper); the
   integration load steps hand `IT_IMAGE=$ID` on, so Compose (Makefile
   treats a `sha256:` IT_IMAGE as prebuilt, never built) and the scan's
   `docker save` (which refuses a non-ID) name the ID. Tests: ci-cache-dir_test
   (ID run, RUNNER_TEMP record, bad record), ci-image_test (a replaced tag
   keeps the record), buildgates `ci_image_id_handoff_test.go` + mutations.

## Out of scope

- Moving the runner's own `_work` or tool cache.
- Sizing raid0 or changing the 40 GB default cap.
