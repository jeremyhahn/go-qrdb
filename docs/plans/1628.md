# Plan: SPEC row rolling-upgrades (#1628)

## Objective

Serve SPEC row rolling-upgrades clauses (1)-(4) and (6) on one row branch:
a node announces its SemVer release version, accepts only adjacent releases
(engineering note Q1) and refuses a peer outside that range with a typed
error naming both versions (QUIC with the TLS no_application_protocol alert
120); a mixed-version cluster (N and N+1) serves every transport, a new Raft
command is used only once every member supports it, a node rolls back
N+1 -> N before activation, and CI runs the N -> N+1 / N+1 -> N matrix as
CLI multi-protocol end-to-end tests.

## Blocked on go-quicraft: proposal-time configuration check

Codex round 2 P1 (pkg/service/service.go AddMember): v0.24.3-alpha compares
configChangeIndex in Host.requestConfigChange before queuing, but its
proposal-time membership validation on the Raft worker does not; an add
that passed the check and paused before enqueue lands after a concurrent
add committed. go-qrdb has no hook on the worker's proposal path, so the
comparison cannot move there from this repository; the go-qrdb-side check
(item 12) narrows the window for ID 0 but cannot close it. The go-quicraft
change needed:

1. Carry the caller's configChangeIndex on the queued config-change
   proposal and, on the Raft worker, where it validates an AddNode /
   AddNonVoting / AddWitness against the current membership immediately
   before appending, refuse with *StaleConfigChangeError when it does not
   match Membership.ConfigChangeID (the in-flight ErrRejected rule already
   serialises uncommitted changes, so that check is exact).
2. Make a comparison against 0 expressible: today 0 means "skip". Add a
   bound form (e.g. a ConfigChangeOption / RequestAdd*At taking an explicit
   "must match" flag, or the index offset by one) so the initial
   configuration is compared on the worker too.
3. A regression test there of the interleaving: add A checked, add B
   commits, A resumes and is refused stale, for voter and observer adds.

Once released, go-qrdb bumps go-quicraft, passes the bound form for every
Required binding, drops Gate.ProposeBound's recheck and lock, and replaces the bindingHost
double's interleaving with a test on the real host.

Codex round 1 at c0ad9cade4 raised it again (pkg/service/service.go
requestAddBound, AddMember and AddObserverMember). Re-checked in the pinned
v0.24.3-alpha: the add validators (validateAddNode, validateAddNonVoting,
validateAddWitness in configChangeValidators) and raft.validateConfigChange
are internal to go-quicraft (pkg/internal/raft/membership.go), with no public
proposal-time hook. The upstream change is tracked as go-quicraft issue 1192;
it covers an explicitly bound ID 0 and an observer add as well as a voter
add, and should take a caller validator so the release recheck below runs
there too. The interleaving test on the real host (not the bindingHost
double) waits on that release. In this PR only the residuals stay open: a
leadership change while an add is in flight, and a member restarted onto
another release whose Gate.Start restart check ran before the add committed
(see "Codex round 3 at 503cc29580").

Codex round 2 at 0e4c729493 raised it again (pkg/service/service.go: bind
release admission at the Raft proposal boundary), now including a member
release that changes after CheckConfigBinding and before the add commits.
Same dependency: it waits on go-quicraft issue 1192 (a caller validator run
on the worker immediately before appending), nothing is implemented for it
here for the worker-side check, and in this PR only the two residuals stay
open (a leadership change mid-add; a restart check that ran before the add
committed); shipping with them open is an owner decision.

Owner ask, option A (recommended): ship with the gap stated, closed by
go-quicraft 1192. The gap is stated in docs/clustering/user.md (Upgrading a
cluster), docs/clustering/engineering.md (Release admission) and the
CHANGELOG.

## Admission reads (#1638, Codex r2 P1)

A member restart changes its release without a configuration change, so
admission must not trust the watch-fed caches. Once started, the gate keeps
its stores and admitRelease reads the advertisements and recorded releases
afresh, refusing with *StoreError when it cannot; the caches still serve
the non-admission paths. Tests (admit_stale_cache_test.go): a stale cached
0.59 advertisement over an authoritative 0.58 refuses a 0.60 candidate; a
release record changed behind the cache refuses it; an unreadable store of
either kind refuses.
