## fx1664t: unique pre-check follows the batch's own writes

- Cause: `CheckUniqueViolationsBatch` took the puts and the deleted keys of a transaction or batch as two unordered lists. It freed a committed unique value only when its holder was deleted, so a batch that overwrote the holder with another value and gave the value to another key was refused although ordered apply admits it; and a put that claimed a value before its holder's delete was admitted by the check and refused at apply.
- Fix: the check takes one ordered `[]indexedWrite` (`writesFromOps` replaces `putsFromOps`/`deleteKeysFromOps` at the KV transaction, MVCC transaction and MVCC batch call sites) and replays it in op order: each write of a key releases the key's committed entries and drops its earlier in-set claims, so a value is free only for later ops; a non-JSON put, or one without the field, releases and claims nothing.
- Tests: `TestCheckUniqueViolationsBatch_OverwriteWithOtherValueFreesValue`, `_NonJSONOverwriteFreesValue`, `_OverwriteAfterClaimRefused`, `_DeleteAfterClaimRefused`, `_OverwriteKeepingValueStillConflicts`, `_RewrittenClaimReleased` (and `_DeletedKeyFreesValue` in the ordered form); `TestMVCCEngine_BatchMovesUniqueValueBetweenKeys` (transaction and batch, both orders); `TestCLIMultiProtocolBatchExecuteMovesUniqueValue` (`qrdb batch execute`, which encodes `protocol.EncodeBatch`, over every protocol; Docker-based, run by CI).
- The KV engine transaction path has no transaction test helper with a unique index in `pkg/engine/kv_engine_test.go`; it shares the check and `writesFromOps`, so it is covered at the check level.
- The non-JSON overwrite form is covered at the check level here; at apply it is covered by fx1664s (which makes a non-JSON overwrite remove the old index entries) once both lanes are merged.
