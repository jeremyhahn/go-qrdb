# Plan: #1647 seal store: embedded-only data, seal/unseal on every transport (docs/18 V12, SealStore half)

#1660 shipped the PermissionClient half. This row ships the SealStore half.

## Objective

Owner ruling 1234: seal-store data is embedded-only. `transport.SealStoreClient`
(Put, Get, Delete, List, Reseal, Status) is served by the embedded transport
alone, gated by `permission.SealStoreManage` (`seal:store_manage`, ScopeCross,
SO-exclusive). Every remote transport (gRPC incl. gRPC-Web, unix, REST, QUIC,
MCP) refuses each verb with the typed `*transport.EmbeddedOnlyError` and no
network I/O; the node serves no seal-store route. Seal and unseal stay on every
transport. The original objective (the seal store on all six transports) is
superseded; Slices 1-6, 8 and 9 below record that superseded work, and the
section "rw1647w1: ruling 1234 embedded-only seal store" records what replaced
it.

## rw1647w3: gRPC-Web SO PIN, errclass rows

### Slice 1: BarrierSeal over gRPC-Web

- Root cause: no transport defect. `BarrierSeal` in the gRPC handler
  (`pkg/api/grpc/service_barrier.go` `qrdbServiceServer.BarrierSeal`) checks
  the barrier SO PIN carried in the request body, `BarrierSealRequest.so_pin`,
  with `pin.RequireSOPIN`; the native SDK (`sdk/go/transport/grpc`
  `BarrierSeal`) sends it there. rw1647w2's gRPC-Web call sent an empty
  `BarrierSealRequest` with only the `x-qrdb-so-pin` header, so the body PIN
  was empty and the backend answered `pin.ErrPINInvalid`. `seal:seal` is not in
  `authmw.SOPermissions`, so `enforceSOGateGRPC` never judges a PIN for it on
  any transport; the gRPC-Web handler forwards headers and body unchanged.
- Fix: none in production code (no relaxed check, no new option).
  `TestSealStore_GRPCWeb_EmbeddedOnly` now seals over gRPC-Web: an empty
  `so_pin` is refused (seen failing first as the brief's header-only call), the
  body PIN seals, status is read over gRPC-Web; the native-gRPC workaround is
  gone. No unit test: there was no package-level cause to reproduce.

### Slice 2: errclass seal-store rows

- Trace: the three sentinels are returned only by `pkg/seal/seal_store.go`;
  its one consumer is `sdk/go/transport/embedded/seal_store.go`, which returns
  the store's error unclassified. `retry_after.go` calls `errclass.RetryAfter`,
  which reads `retryAfterRules`, not the class table. No remote handler serves
  the store (ruling 1234).
- Decision: delete the three rows in `pkg/api/errclass/table.go` and the two
  `ErrInvalidSecretName` cases in `classify_test.go` (no compat surface).
- `docs/barrier-seal/api.md` and `CHANGELOG.md`: a sealed node's embedded
  client sees `seal.ErrSealed` (the node seal gate runs first);
  `ErrSealStoreBarrierSealed` is the store's guard behind it. The CHANGELOG no
