# Plan: #1765 conditional pending -> active activation (ActivatePending)

Objective: credential-first flows (go-xkms #2270) activate a PENDING account
with one conditional commit; any other lifecycle (active, disabled, deleting,
or one committed between the caller's read and the write) is refused with
`*AccountNotPendingError` and nothing is written. UpdateUser is unchanged.

## Slices

1. Store (this slice): `user.PendingActivator` interface beside
   `CertActivator`; `kvUserStore.ActivatePending` mirroring the
   conditional-commit retry of `ActivateWithCertBinding`;
   `routingUserService.ActivatePending` routing on the owning tenant.
   Tests (pkg/user/activate_pending_test.go): pending -> active; active,
   disabled, deleting refused with the record unchanged; a disable committed
   between read and commit refused; concurrent calls have one winner; zero
   id and missing user.
2. Transports (after #1764 lands its SDK error pattern): SDK
   `transport.AccountNotPendingError{ID, Lifecycle, HasCredential}` with a
   structured-refusal reason and errclass entry; `ActivatePending` on gRPC
   (proto + handler), REST, QUIC, MCP, and SDK embedded/grpc/rest/quic/mcp/
   unix plus `UserClient`; same permission as EnableUser; SDK tests against
   a real node, standalone and raft (DisableUser first -> refused; two
   concurrent calls -> one winner, account active); docs user API pages.

## Out of scope

#1764 (SDK ActivateWithCertBinding); UpdateUser semantics; docs/SPEC.md;
go.mod; coverage baselines; key or credential handling.
