# Plan #1478: backup verify and restore against a real server

## Objective

A DOM-tier Playwright spec (`cmd/qrdb/frontend/e2e/dom/backup-restore-roundtrip.spec.ts`)
that verifies and restores a backup through BackupManager against a live
daemon, and proves on the server that the original data is back.

## Slices

1. UI fixes in BackupManager found by the spec:
   - the restore modal has no plaintext opt-in, so the server refuses every
     restore of a plaintext backup (`allowPlaintext`); add an explicit checkbox;
   - no way to pick target shards (`targetShards`); add a field;
   - `RestoreResult.duration` does not exist on the wire (`duration_ms`); the
     toast read "restored in undefined". SDK type is `durationMs`; the mock
     double returned the non-existent field and is corrected;
   - per-shard restore errors are shown in the toast, not only counted.
   Tests: mocked `e2e/backup-manager.spec.ts` asserts the exact toast.
2. DOM spec:
   - verify: the Verify button shows "verified OK" and the server's
     POST /v1/backups/{id}/verify agrees;
   - refused restore: without the opt-in the server's error is the toast;
     a restore of a backup deleted behind the UI shows the server's error;
   - restore: keys changed and deleted through /kv come back after a UI
     restore with validate-first on.

## Open finding

On a single-node daemon every database lives in the system shard (1), and the
server refuses online restore of shard 1 (it points to the offline
`qrdbd start --restore-backup-id` flow). A successful online restore needs a
non-system shard with one voting replica: likely a dedicated raft database
(`replicas: 1`) on the DOM cluster fixture (`startCluster`). Next slice.

## Out of scope

Go server changes; the offline restore boot flow; docs/SPEC.md and the
coverage matrix (coordinator).

## User update, disable/enable and cert bindings against a real server

Lane dqrucert wrote this part on main; it was cherry-picked onto the #1479
head, where lane guser2 had already added the same controls.

### Objective

The admin UI drives every user operation the backend offers, proven by a
DOM-tier Playwright spec against a live qrdbd: update, disable, enable,
add/remove a certificate binding, and look a user up by certificate
thumbprint.

### Findings at the base (main)

- `UserDetail.svelte` only called `users.update`; it had no disable/enable
  or certificate-binding controls.
- `UserManager.svelte` had no lookup by certificate thumbprint.
- The SDK `User` type did not carry `certBindings`, although the REST
  server returns `cert_bindings` on every user.

### Slices

1. SDK: `User.certBindings?: readonly CertBinding[]` (thumbprint, kind,
   notAfter), exported from the package index.
2. UserDetail: the Disable/Enable buttons and the Certificate Bindings card
   already on the head (lane guser2) stay, with their testids; the binding
   list is now read from the server's `certBindings` on load and after each
   add/remove, not kept only in the view. Errors surface the server's
   message in a toast.
3. UserManager: the head's "Find user by certificate thumbprint" form opens
   the matching user, and a 404 now reports that no user holds the binding.
4. `e2e/dom/user-detail-roundtrip.spec.ts` (seal "none"):
   - create a user, rename it in UserDetail, check GET /users/{id};
   - disable then enable; check the server lifecycle and the UI buttons;
   - openssl self-signed cert -> SPKI SHA-256 thumbprint; add the binding
     in the UI, check the server lists it, look it up in UserManager,
     remove it, check the lookup now finds nobody;
   - a malformed thumbprint is refused and the server's error shows.

### Departures found while building

- The fixture's seal "none" no longer boots (server: auth.enabled requires
  seal.enabled), so the spec uses "none-committed" and initializes through
  POST /v1/ceremony/initialize (so_pin, user_pin, admin_generate).
- Create User was refused by the server (email required) because the form
  had no email; lane guser2 had already fixed that on the head (email at
  create, blank = withoutEmailLoginKey). Kept from dqrucert: the SDK
  `name` on create and `email`/`name` on update and on User, and the Email
  field on edit plus a Display Name field in UserDetail.
- The users routes are unprefixed (/users/...), not /v1/users.
