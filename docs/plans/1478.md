# Plan #1478: backup verify and restore against a real server

## Objective

A DOM-tier Playwright spec (`cmd/qrdb/frontend/e2e/dom/backup-restore-roundtrip.spec.ts`)
that verifies and restores a backup through BackupManager against a live
daemon, and proves on the server that the original data is back.

## Slices

1. UI fixes in BackupManager found by the spec:
   - the restore modal has no plaintext opt-in, so the server refuses every
     restore of a plaintext backup (`allowPlaintext`); add an explicit checkbox;
   - no way to pick target shards (`targetShards`); add a field;
   - `RestoreResult.duration` does not exist on the wire (`duration_ms`); the
     toast read "restored in undefined". SDK type is `durationMs`; the mock
     double returned the non-existent field and is corrected;
   - per-shard restore errors are shown in the toast, not only counted.
   Tests: mocked `e2e/backup-manager.spec.ts` asserts the exact toast.
2. DOM spec:
   - verify: the Verify button shows "verified OK" and the server's
     POST /v1/backups/{id}/verify agrees;
   - refused restore: without the opt-in the server's error is the toast;
     a restore of a backup deleted behind the UI shows the server's error;
   - restore: keys changed and deleted through /kv come back after a UI
     restore with validate-first on.

## Open finding

On a single-node daemon every database lives in the system shard (1), and the
server refuses online restore of shard 1 (it points to the offline
`qrdbd start --restore-backup-id` flow). A successful online restore needs a
non-system shard with one voting replica: likely a dedicated raft database
(`replicas: 1`) on the DOM cluster fixture (`startCluster`). Next slice.

## Out of scope

Go server changes; the offline restore boot flow; docs/SPEC.md and the
coverage matrix (coordinator).
