# Plan: admin Settings view against a real server (#1478)

## Objective

The admin Settings view (`cmd/qrdb/frontend/src/views/admin/Settings.svelte`)
shows values that match the server and its Disconnect action works, proven by
a DOM-tier Playwright spec against a real qrdbd
(`e2e/dom/settings-roundtrip.spec.ts`, `playwright.dom.config.ts`).

## Slices

1. DOM spec, seal "none" daemon:
   - About table `server` row equals the server's `/status` `node_id` (what
     the REST SDK's `connection.getVersion()` reports; qrdbd has no separate
     version route), `sdk` row is non-empty.
   - Connection badge reads Connected; Server card's Initialized matches
     `GET /v1/config/initialized`; Embedded server available is No (REST).
2. Disconnect from Settings: badge reads Disconnected, the button disables,
   the server still answers `/health`; the header Connect button reconnects
   and the badge reads Connected again; a fresh page load also connects.
3. UI fix (own commit): web-mode `connectProfile` reopens a REST transport
   closed by `connection.disconnect()` (Settings' Disconnect left the app
   stuck until a reload), and Settings re-reads
   `client.connection.isConnected()` when the active profile's connection
   state changes, so a reconnect while the view is open shows Connected.

## Out of scope

- Server (Go) changes, SDK changes (`sdk/typescript/src/rest.ts` is owned by
  another lane), a server version route.
- docs/SPEC.md and docs/gui/coverage-matrix.md (coordinator).
# Plan: tenant update and delete against a real server (#1478)

## Objective

The admin UI's tenant update (`views/admin/TenantDetail.svelte`,
`client.tenants.update`) and tenant delete (`views/admin/TenantManager.svelte`,
`client.tenants.delete`) are driven end to end against a live `qrdbd` in the
DOM tier, with the server state checked over the REST API.

## Slices

1. `cmd/qrdb/frontend/e2e/dom/tenant-update-roundtrip.spec.ts`, booted like
   `tenant-management.spec.ts` (`startDaemon({ seal: "none" })`):
   - update: create a prefix tenant, open it, rename it in the info card,
     Save, expect the `Tenant "<id>" updated.` toast, the field shows the new
     name and `GET /v1/tenants/{id}` returns it;
   - refused update: the server accepts every isolation change on an empty
     tenant and keeps the old name on an empty one, so the refusal used is
     a tenant deleted on the server while its form is open: Save shows the
     server's not-found error in a toast and nothing is written;
   - delete: select the tenant row in the Tenants list, Delete Selected,
     confirm the dialog, expect the `Deleted 1 tenant.` toast, the row is
     gone from the UI and `GET /v1/tenants` no longer lists it while
     `GET /v1/tenants/{id}` is 404.
2. A UI defect the spec exposes is fixed in its own commit in the view.

## Tests

`npx playwright test --config=playwright.dom.config.ts
e2e/dom/tenant-update-roundtrip.spec.ts`; `npm run check` 0 errors.

## Out of scope

Go server code, the SDK, `docs/SPEC.md` and `docs/gui/coverage-matrix.md`
(the coordinator updates the matrix row), the real-backend API-only tier.
# Plan #1478: backup verify and restore against a real server

## Objective

A DOM-tier Playwright spec (`cmd/qrdb/frontend/e2e/dom/backup-restore-roundtrip.spec.ts`)
that verifies and restores a backup through BackupManager against a live
daemon, and proves on the server that the original data is back.

## Slices

1. UI fixes in BackupManager found by the spec:
   - the restore modal has no plaintext opt-in, so the server refuses every
     restore of a plaintext backup (`allowPlaintext`); add an explicit checkbox;
   - no way to pick target shards (`targetShards`); add a field;
   - `RestoreResult.duration` does not exist on the wire (`duration_ms`); the
     toast read "restored in undefined". SDK type is `durationMs`; the mock
     double returned the non-existent field and is corrected;
   - per-shard restore errors are shown in the toast, not only counted.
   Tests: mocked `e2e/backup-manager.spec.ts` asserts the exact toast.
2. DOM spec:
   - verify: the Verify button shows "verified OK" and the server's
     POST /v1/backups/{id}/verify agrees;
   - refused restore: without the opt-in the server's error is the toast;
     a restore of a backup deleted behind the UI shows the server's error;
   - restore: keys changed and deleted through /kv come back after a UI
     restore with validate-first on.

## Open finding

On a single-node daemon every database lives in the system shard (1), and the
server refuses online restore of shard 1 (it points to the offline
`qrdbd start --restore-backup-id` flow). A successful online restore needs a
non-system shard with one voting replica: likely a dedicated raft database
(`replicas: 1`) on the DOM cluster fixture (`startCluster`). Next slice.

## Out of scope

Go server changes; the offline restore boot flow; docs/SPEC.md and the
coverage matrix (coordinator).
