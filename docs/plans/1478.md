# #1478 — user update, disable/enable and cert bindings in the UI, against a real server

## Objective

The admin UI drives every user operation the backend offers, proven by a
DOM-tier Playwright spec against a live qrdbd: update, disable, enable,
add/remove a certificate binding, and look a user up by certificate
thumbprint.

## Findings at the base

- `UserDetail.svelte` only called `users.update`; it had no disable/enable
  or certificate-binding controls.
- `UserManager.svelte` had no lookup by certificate thumbprint.
- The SDK `User` type did not carry `certBindings`, although the REST
  server returns `cert_bindings` on every user.

## Slices

1. SDK: `User.certBindings?: readonly CertBinding[]` (thumbprint, kind,
   notAfter), exported from the package index.
2. UserDetail: Account Status card (lifecycle badge, Disable/Enable) and a
   Certificate Bindings card (list, add by SPKI thumbprint with optional
   expiry, remove). Errors surface the server's message in a toast.
3. UserManager: "Find by certificate thumbprint" field that opens the
   matching user, or reports that no user holds the binding.
4. `e2e/dom/user-detail-roundtrip.spec.ts` (seal "none"):
   - create a user, rename it in UserDetail, check GET /v1/users/{id};
   - disable then enable; check the server lifecycle and the UI badge;
   - openssl self-signed cert -> SPKI SHA-256 thumbprint; add the binding
     in the UI, check the server lists it, look it up in UserManager,
     remove it, check the lookup now finds nobody;
   - a malformed thumbprint is refused and the server's error shows.

## Departures found while building

- The fixture's seal "none" no longer boots (server: auth.enabled requires
  seal.enabled), so the spec uses "none-committed" and initializes through
  POST /v1/ceremony/initialize (so_pin, user_pin, admin_generate).
- Create User was refused by the server (email required) because the form
  and the SDK request types had no email: the SDK Create/UpdateUserRequest
  and User gain email and name, and UserDetail gains Email and Display Name.
- The users routes are unprefixed (/users/...), not /v1/users.

## Out of scope

Go server code, docs/SPEC.md, docs/gui/coverage-matrix.md, rest.ts.

# #1478 part 4 — time series, seal and ceremony, cluster operations

## Objective

Close docs/gui/coverage-matrix.md gap groups 9 (Time series), 10 (Seal and
ceremony) and 11 (Cluster operations): every listed SDK method and display
is reachable from the UI and proven by a mocked Playwright spec, with a
DOM-tier round trip against a live qrdbd where the matrix asks for one.
The work is replayed from the reference lane (lane/gui1478a), these groups
only. Part 1 (above) landed on main first; this part merges main on top.

## Slices

1. Time series (group 9): TimeSeriesView gains batch write, aggregate,
   rich query and retention cards; the single-point Write takes a point.
   Tests: e2e/timeseries-advanced, timeseries-ops, timeseries-write-point;
   e2e/dom/timeseries-advanced-roundtrip.
2. Seal and ceremony (group 10): SealManager shows every cluster seal field
   and the cluster migration progress, unseals the cluster, changes the
   passphrase, and has a ceremony card (state, SPKI pin, sign CSR).
   Tests: e2e/admin-seal; e2e/dom/cluster-seal-roundtrip,
   cluster-seal-active-roundtrip, ceremony-passphrase-roundtrip.
3. Cluster operations (group 11): Cluster mints a join token and reads and
   sets node compaction; RebalancePanel shows a shard's stats.
   Tests: e2e/admin-cluster, rebalance-panel, web-mode-cluster,
   web-mode-cluster-detection; e2e/dom/cluster-topology,
   rebalance-roundtrip, node-compaction-roundtrip, join-token-roundtrip.
4. Matrix: these groups' operation and display rows verified, the groups
   marked covered, the summary counts recomputed for them.

## Smallest pieces taken from other groups

- DOM fixtures (cluster passphrase, per-test client certificate through
  the Vite proxy) the DOM specs import.
- A single-node Raft server is "raft" (the Cluster view mints its first
  join token there); isMultiNodeServer keeps the wizard's replica and
  Raft steps for multi-node servers.
- REST SDK wire fixes the views need: shard stats path, the time-series
  aggregate, rich query and retention routes and point encoding.
- Database wizard create no longer sends engine and mode, which the
  server's strict decoder refuses (main's own DOM timeseries spec failed).
- Review fixes (#1612): batch values must be whole finite numbers; the
  aggregation menus offer only the REST aggFuncMap functions (avg, sum,
  min, max, count, percentile); closing pending shard stats drops the
  lookup and re-enables Load Stats; the Scenario E2 spec fills the unseal
  field by test id (the ceremony card adds password fields after it).
- Review fixes (#1612, round 2): the desktop SealBinding.Status marks a
  cluster-held node (503 SEALED) with clusterHeld, so the Seal Manager offers
  Clear Cluster Seal through Wails too; time-series aggregate, rich query,
  points and retention responses carry a metric generation and are dropped
  after a metric switch; a failed retention lookup shows an error with Retry,
  never "Current policy: none". Specs: admin-seal (held via Wails),
  timeseries-ops (stale aggregate, retention error); Go binding unit test.

## Out of scope

Other gap groups, Go server code, docs/SPEC.md, playwright.real.config.ts.
