# Plan: strict-tenant-isolation phase 7, PN-4 unseal fan-out (#683)

## Objective

`qrdb tenant barrier-unseal` reaches every node serving the tenant
barrier, as `barrier-init` already does, so a tenant whose shards serve
on several nodes is unsealed on all of them, not only on `--server`'s.

## Slices

1. Unseal fan-out (cmd/qrdb/tenant.go). barrier-unseal reads
   `--server`'s barrier status; when more than one node serves the
   barrier it sends the unseal to each through `runOnServingNodes`
   (one result line per node, `BarrierFanOutError` naming the nodes
   that refused); one serving node stays on `--server`'s client.
   Tests (cmd/qrdb/tenant_barrier_fanout_test.go):
   - TestTenantBarrierUnseal_FansOutToServingNodes: three serving
     nodes each receive the unseal; the refusing one is named in the
     `BarrierFanOutError`, the other two unseal.
   - TestTenantBarrierUnseal_SeveralNodesFanOut: on rest, grpc, quic
     and mcp the CLI sends the unseal to every node and not to
     `--server`'s node.
   - TestTenantBarrierUnseal_OneNodeUnsealsServerNode.
2. Docs: the PN-4 bullet of docs/multi-tenancy/engineering.md and any
   barrier-unseal CLI doc say unseal fans out like init.

## Out of scope

- A `tenant barrier-rekey` command: none exists, none is added here.
- Strategy gating of the unseal fan-out: init fans out only for the
  passphrase strategy; unseal has no strategy flag and fans out
  whenever several nodes serve the barrier.
- Lower-layer (go-quicraft, go-enclave) changes; go.mod changes.
