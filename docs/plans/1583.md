# Plan: user lifecycle state — pending users with a TTL (#1583)

Owner ruling 632 item 221 C; consumer go-xkms webauthn row #2202.

## Objective

A user can be created pending with a time-to-live. A pending user cannot log
in or get a session; activating it (EnableUser, idempotent) makes it active and
clears the TTL, and nothing transitions back to pending. A leader-only reaper
deletes pending users past their TTL — role assignments and enrolled factors
with them — audits each removal, and never touches an active user. Served on
every transport, the CLI and sdk/go, per tenant.

## What already exists (base 71a2077)

- `user.Lifecycle` with pending/active; `CreateUserRequest.Pending` and
  `.Lifecycle`; no transition into pending (`lifecycleTransitions`).
- `Lifecycle.CanAuthenticate` refuses pending at login and session issue.
- `EnableUser` is the activate operation on REST, gRPC, QUIC, MCP, embedded.

## Slices

1. **Model + store + reaper (pkg/user).**
   - `User.PendingExpiresAt` (RFC 3339, omitted when unset);
     `CreateUserRequest.PendingTTL` (refused unless the create is pending,
     refused when negative; zero = no expiry).
   - `applyLifecycle` clears `PendingExpiresAt` on any move out of pending.
   - `PendingReaper`: injected clock, injected leadership check, a user
     servicer and an optional factor purger; `Sweep(ctx, tenantID)` lists
     the tenant's users, deletes pending ones past expiry (re-checked on a
     fresh read), removes their factors, audits `pending_reaped`.
   - Reap order is **claim, purge, delete**. `ClaimExpiredPending` durably
     marks the account deleting (conditionally on the pending version it
     read, so an activation that lands first wins) and records the expiry
     in `ExpiryClaim`. The factor service's `Purge` then seals the user's
     factor set (later enrollments are refused) and removes every factor,
     revoked ones included, with their credential indexes. Last,
     `DeleteExpiredPending` removes the account. A failure after the claim
     leaves the account claimed in the store; every later sweep, by any
     reaper on any leader, lists it (`ExpiryClaimed`) and resumes. The
     reaper keeps no in-memory retry state.
   - Tests: TTL validation, expiry stamped from the clock, activate clears
     TTL and is idempotent, no transition back to pending, reaper removes only
     expired pending users, skips active/unexpired/no-TTL users, does nothing
     off-leader, audits each removal.
2. **Wiring.** Reaper started on the node for standalone and Raft (leader
   gate from the Raft node; standalone always leader), per tenant via the
   routing service, ticker from config.
3. **Transports.** `pending_ttl` on create and `pending_expires_at` on read
   for REST, gRPC (proto), QUIC, MCP, embedded; CLI `users create --pending
   --pending-ttl`; sdk/go fields. E2E: create pending with TTL, login
   refused, activate, login succeeds, on every transport.
4. **Docs.** docs/users (identity) and CHANGELOG.

## Status

All four slices are done. Slice 3 also covers the Unix transport, which serves
the gRPC service. Wire names:

- REST: `pending_ttl` (duration) and `pending_expires_at` (RFC 3339).
- gRPC and Unix: `pending_ttl_seconds` and `pending_expires_at_unix`.
- QUIC: `pendingTTL` and `pendingExpiresAt`.
- MCP: `pending_ttl` and `pendingExpiresAt`.
- sdk/go: `PendingTTL` and `PendingExpiresAt`.

The E2E is `TestUsers_CLI_PendingTTL_PerProtocol` in the identity_rbac feature
target. The sweep period is `auth.pending_user_sweep_interval` (default `1m`,
`off` disables).

Review follow-ups: a plain `DeleteUser` of an account the reaper claimed
keeps its reap marker, so the next sweep purges the factors and audits
`pending_reaped` once (test: failed purge, DeleteUser, sweep). TTLs are
gated on the `pending-user-ttl` cluster feature (`user.WithPendingTTLGate`):
before activation a TTL create returns `feature.NotActiveError` and
`PendingReaper.Sweep` touches nothing.
