# #1745: accepting an existing run-mode marker makes its directory durable first

## Objective

`lifecycle.ClaimRunMode` accepts a present marker that names the configured
mode. If the first claim's `fsync.Rename` wrote the marker but its directory
sync failed, the marker may not survive power loss, so a later same-mode claim
must not succeed on it until the data directory has been synced; otherwise an
opposite-mode start after a crash can bypass the run-mode guard (Codex P1 on
#1734, ruling 1378 review debt).

## Slice 1

- `pkg/server/lifecycle/run_mode.go`: `checkRunMode`, used both by
  `ClaimRunMode`'s first read and by `writeRunMode`'s re-read under the lock,
  calls `fsync.Dir(dataDir)` before accepting a matching marker and returns
  `*RunModeMarkerError` wrapping the sync error. Mismatch and unknown-marker
  paths are unchanged.
- Test `TestClaimRunMode_ExistingMarkerSyncsDir`: matching marker, directory
  sync failing via `fsync.SetForTest` -> `ClaimRunMode` error `errors.Is` the
  injected error; restored sync -> claim succeeds.
