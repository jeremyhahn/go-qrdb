# #1764 — ActivateWithCertBinding on transport.UserClient

## Objective

Expose the store's conditional activation (`user.CertActivator`,
`kvUserStore.ActivateWithCertBinding`) as an authenticated user operation on
every transport, so go-xkms (#2270) can activate a pending account with its
first certificate binding in one commit, and learn of a lost race through a
typed error rather than text.

## Design

- `transport.AccountNotPendingError{ID, Lifecycle, HasCredential}` is the one
  type; `pkg/user.AccountNotPendingError` is an alias of it (the
  `ConcurrentUpdateError` precedent), so embedded callers get it unchanged.
- It travels as the `ACCOUNT_NOT_PENDING` structured refusal
  (`errclass.Refusal` -> `transport.RefusalError`) with class
  FailedPrecondition, distinct from validation, `CertBindingExpiredError` and
  store errors.
- Authorization reuses `users:add_cert_binding` and
  `AuthMiddleware.AuthorizeCertBindingTarget` on every transport.
- Handlers call `user.ActivateWithCertBindingOn(svc, ...)`, which refuses a
  user service that is not a `CertActivator` with `ErrActivationUnsupported`.
  There is no pkg/service step: AddCertBinding has none either.
- Wire: gRPC/unix `QRDBService.ActivateWithCertBinding`; REST
  `POST /users/{id}/activate-with-cert-binding`; QUIC
  `user.ActivateWithCertBinding`; MCP `qrdb_user_activate_with_cert_binding`.

## Slices

1. SDK method + server handlers on every transport + typed refusal.
   Tests: refusal round trip in errclass and sdk/go/transport; each server
   handler maps the refusal; SDK test against a real node per harness
   transport, standalone and raft: N=8 concurrent activations of one pending
   account -> exactly one succeeds, the rest `*AccountNotPendingError`;
   a disabled account is refused and keeps no binding.

## Out of scope

- #1765 ActivatePending (lane rw1765a); docs/SPEC.md; go.mod; coverage
  baselines; key or credential handling.
