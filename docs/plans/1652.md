# Plan: #1652 sdk/go re-exports the RBAC permission matcher

Row: `sdk-rbac-authorization-reexport` (docs/SPEC.md), seam with
go-quicbaas D5.

## Objective

A consumer of the Go SDK (go-quicbaas D5) must decide "does this grant
admit that permission" with the server's own rule, not a fork of it. The
rule lives today in the unexported `permissionGranted` in
`pkg/auth/rbac/rbac.go`. Move it to `pkg/permission` as two exported
functions and re-export both from `sdk/go`.

## Slices

1. `pkg/permission`: `Matches(granted, required Permission) bool` and
   `Granted(held map[Permission]struct{}, required Permission) bool`.
   Whole-segment wildcards only: exact `resource:action`, `resource:*`,
   `*:action`, `*:*`. `Granted` stays the O(1) set lookup.
   Tests first: table test (exact, resource wildcard, action wildcard,
   full wildcard, glob prefix `ke*:sign` refused, other resource refused,
   empty set refused), and `Granted` agrees with `Matches` over the set.
2. `pkg/auth/rbac`: `Authorize` calls `permission.Granted`;
   `permissionGranted` deleted outright (no wrapper). Existing rbac tests
   cover the behaviour.
3. `sdk/go`: `PermissionMatches = permission.Matches`,
   `PermissionGranted = permission.Granted`. Test
   `types_permission_matcher_test.go`: for the same grants, the aliases
   answer as `rbac.New(...).Authorize` does.
4. Docs: the SPEC row amended in place (Permissions list + go-quicbaas D5
   consumer), `docs/identity-rbac/api.md` wildcard text names the matcher.

## Out of scope

No wire API, transport or CLI change (SDK-only). No change to the
wildcard rule itself, to `Expand`, or to role validation.
