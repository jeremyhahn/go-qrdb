# Plan: SQLite VFS backend, tier 1 (#926)

## Objective

Build the first build slice that
[../decisions/sqlite-vfs-build.md](../decisions/sqlite-vfs-build.md)
("First build slice the recommendations imply") implies: a pure-Go page store
in the root module that maps one SQLite database file onto the
`sqlite/<db>/meta` and `page/<pgno>` keyspace with snapshot-pinned reads, a
one-proposal commit, the staged commit and publish for oversized transactions
(Q2 A), a serialized writer through a distributed lock with `SQLITE_BUSY` on
contention (Q3 A), the restore generation check (Q4 A), quota accounting with
`SQLITE_FULL` and the `sqlite-vfs` entitlement (Q5 A); then a tier 1 binding
on `modernc.org/sqlite` registering VFS `qrdb` (Q1 A), tested end to end by a
stock SQLite application on every transport.

Rulings: Q1-Q5 A adopted (Tenant Agent ruling 1115, 2026-11-22); the SQLite
engine dependency is pending the owner (owner queue 288); no engine import
until he answers.

## Slices (in order)

1. Page store core (sr926a, done): keys, meta record, `Txn` over `Backend`,
   `MVCCBackend`; unit tests of keys, meta, reads, writes, truncation,
   snapshot isolation and atomic commit.
2. Staging and generation (sr926b, done): staged commit and one publish above
   the stage threshold, meta restore generation, `ErrSnapshotChanged` at Begin
   and Commit, `Store.BumpGeneration`; unit tests of staged commit, publish
   and stage failure cleanup, generation change.
3. Writer lock, change counter, stage sweep (sr926c, done):
   `WriterLock` over `lock.Locker`, `Txn.Reserve` (xLock RESERVED) with
   `ErrBusy` at once on contention, `ErrBusy` at Commit on a lost lease, the
   meta change counter so a stale snapshot cannot reserve, and the sweep of
   stages a crashed writer left; unit tests with an in-package `lock.Locker`.
4. Server-side prefix-move publish op (sr926d, done):
   `protocol.OpMVCCMovePrefix` behind the `prefix-move` cluster feature,
   `MVCCKVService.MovePrefix`, and its rewrites in the namespace,
   hard-confinement and quota wrappers; one revision, a live-count mismatch
   writes nothing.
5. Page store publish over `MovePrefix` and a service-backed Backend (sr926e
   and sr926f, done).
6. Deps step: add `modernc.org/sqlite` to `go.mod` (its own step) (blocked:
   owner queue 288).
7. Tier 1 binding and VFS `qrdb` registration (Q1 A) (blocked: owner queue
   288): batch-atomic, no WAL,
   no `xShmMap`, the true journal mode reported; error mapping
   (`ErrBusy` to `SQLITE_BUSY`, `ErrSnapshotChanged` to
   `SQLITE_BUSY_SNAPSHOT`).
8. Server wiring (sr926g, done): the writer lock over the server's
   lock service (`NewLockServiceWriter`), and a Store over a (tenant,
   database) scope's resolved MVCC, transaction and lock services, its commit
   and staged publish one proposal each through the service-backed Backend,
   proven on the prefix, volume and raft isolation types. Open for the owner:
   - (o1) where and by whom the server constructs a Store for a caller
     (registry accessor, embedded-server SDK surface or transport op).
   - (o2) the holder ID a database's writer takes (per connection, process
     or node) and the default lease TTL. Decided by convention (ruling 109):
     per connection, and the lease TTL is the lock service's default TTL.
   - (o3) whether the Backend carries a per-call context instead of
     ServiceBackend's construction-time context. Decided by convention
     (ruling 109): the Backend takes a per-call context. Built (sr926j): every Backend method takes a context.Context, and Store.Begin pins the transaction's read context.
   - (o4) whether the prefix-move op is wrapped in OpGuarded. Decided by
     convention (ruling 109): it is OpGuarded. Built (sr926j): the namespaced view's MovePrefix carries the database's drop-fence guard, so the move is one OpGuarded entry, proven by a drop racing a staged publish.
9. Quota and `SQLITE_FULL` (sr926h and sr926i, done): a commit or publish past
   the tenant's storage quota fails with `ErrFull` (the binding maps it to
   `SQLITE_FULL`) and leaves the database whole, proven on the prefix, volume
   and raft isolation types. The per-tenant database count cap and the
   `sqlite-vfs` entitlement gate a database's creation. They are built as a
   gate that takes its inputs (slice 9b, rw926c below), and the admin
   surface that sets both on every transport, the CLI and config defaults is
   built (slice 9c, rw926d below); only the gate's caller, where the server
   constructs a Store (o1), waits on the owner's answer.
10. Optimistic mode (`qrdb_concurrency=optimistic`, Q3) (rw926a, done):
   `WithOptimistic`, the opt-in alternative to `WithWriterLock` (the two are
   exclusive: `ErrOptimisticWithWriterLock`). A transaction records every page
   it reads from its snapshot, including pages read as absent, as a
   `ReadCheck` set. `Backend.Commit` and `Backend.Publish` check it
   atomically with the write: `MVCCBackend` under its lock, and
   `ServiceBackend.Commit` as compares in the commit's own transaction. A
   changed read fails with `ErrSnapshotChanged` and writes nothing. Unit
   tests cover disjoint writers, an overlapping read, an absent page created
   concurrently, a staged commit conflicting at publish (its stage keys
   swept), and the conflict over the service. Departures and open items:
   - The meta key is checked at the commit-time revision, not the snapshot
     revision. Every commit rewrites meta, so a snapshot-revision check would
     make every pair of writers conflict. This check makes the generation check
     atomic with the write for any Store without a writer lock. Optimistic mode
     conflicts instead on a moved page count or page size, and advances the
     change counter from the newest meta record.
   - (o5, closed by rw926b) `OpMVCCMovePrefix` carries compares, which the
     engine evaluates at apply before it reads the source range, atomically
     with the move; a failed one answers a guard refusal
     (`*service.WriteGuardRefusedError`) and writes nothing.
     `ServiceBackend.Publish` sends the read set as those compares and maps
     a failed one to `ErrSnapshotChanged`, so a staged commit over the
     service without a writer lock is read-checked, not refused. The
     compares travel in the existing
     op behind the `prefix-move` feature. Tests: protocol roundtrip and
     truncations, engine failed-compare and absent-key compares, service
     and wrapper handling, `TestOptimistic_ServiceStagedPublishConflicts`,
     and `TestSQLiteVFSWiring_OptimisticStagedPublishChecksReads` on the
     prefix, volume and raft isolations.
   - (o6) SQLite rewrites page 1 (the file change counter at offset 24) on
     every write transaction. Once the binding (slice 7) runs, two optimistic
     SQLite writers therefore always overlap on page 1 and conflict, even when
     their data pages are disjoint. Concurrent optimistic writers need the
     binding to exclude the header's change-counter bytes from the read check,
     or to serve them from the meta change counter. This is for slice 7 to
     decide.
11. CLI end-to-end tests per the test standard on every transport (gRPC,
   QUIC, Unix, embedded): commit, contention and busy-retry, a `VACUUM`
   above the stage threshold, restore to a revision, quota exhaustion.

## rw926c

Slice 9b: the `sqlite-vfs` entitlement and the per-tenant SQLite-database
count cap (Q5 A) as an admission gate over the page store.

- `quota.FeatureSQLiteVFS` (`"sqlite-vfs"`) with
  `Entitlements.AllowSQLiteVFS` (`allow_sqlite_vfs`, false by default, fail
  closed), and `Quotas.MaxSQLiteDatabases` (`max_sqlite_databases`) with
  `quota.ResourceSQLiteDatabases` (`"sqlite_databases"`), appended last in
  every resource table. A limit of 0 or -1 is unlimited, as for
  `MaxDedicatedWALGroups`.
- `sqlitevfs.Admit(ctx, backend, tenantID, db, ents, lim)` validates the
  name, admits an existing database (a live meta record at the newest
  revision) with no check, and otherwise checks the entitlement and then the
  count. The system tenant is implicitly entitled and uncapped.
  `sqlitevfs.CountDatabases` counts the meta keys in the tenant's own
  `sqlite/` keyspace. The caller registers it as the resource's quota
  counter.

Departures and open items:

- The count cap is a soft bound. Two concurrent creators can both pass at
  the limit minus one. The cap limits growth, and the storage quota is the
  hard bound.
- Admit creates nothing. The first committed transaction creates the
  database, as before.
- (o1) is still open. Nothing in the server calls Admit yet, and no
  registry accessor, SDK surface or transport op constructs a Store.
- The proto, REST, gRPC, QUIC, MCP, CLI and SDK fields for
  `allow_sqlite_vfs` and `max_sqlite_databases`, and the config defaults,
  are built in rw926d (below).

Tests: `pkg/quota/sqlite_vfs_entitlement_test.go` (feature default and
grant, resource name and tables, JSON), `pkg/sqlitevfs/admission_test.go`
(refusals, the existing database, a bad name, the system tenant, and meta-only
counting, including a page number that spells `meta`), and
`TestSQLiteVFSAdmission_*` in `pkg/server`, which run the real
`quota.Service` over the registry's services on the prefix, volume and raft
isolation types. The other tenant's databases never count.

## rw926d

Slice 9c: the admin surface for the `sqlite-vfs` entitlement and the
SQLite-database count cap.

- Proto: `TenantEntitlements.allow_sqlite_vfs` (field 8) and
  `TenantQuotas.max_sqlite_databases` (field 17).
- Server transports: gRPC, QUIC and Unix (the shared tenant handlers), REST
  (quotas PUT and entitlements PATCH) and MCP (update-quotas and
  update-entitlements tools) map both fields both ways.
- SDK: the Go transport types and the embedded, gRPC, QUIC, Unix and MCP
  transports (through `tenantconv`), and the TypeScript types.
- CLI: `qrdb tenant set-entitlement --allow-sqlite-vfs` and
  `qrdb tenant update-quotas --max-sqlite-databases`.
- Config: `tenant.default_entitlements.allow_sqlite_vfs` (default `false`)
  and `tenant.default_quotas.max_sqlite_databases` (default `0`, unlimited)
  through `ToEntitlements` / `ToQuotas`.

Tests: the gRPC, QUIC, REST and MCP tenant handler tests, the config
defaults test, the Go SDK transport and `tenantconv` tests, the `qrdb tenant`
flag tests, and the CLI e2e `TestCLIMultiProtocolTenantSetEntitlement`
(extended) and `TestCLIMultiProtocolTenantUpdateQuotasSQLiteDatabases` in
`test/integration/api/cli_tenant_barrier_test.go`.

Open: (o1) is still open. Nothing in the server calls `Admit`, and nothing
registers `CountDatabases` as the `sqlite_databases` quota counter; that
waits on the owner's answer with the Store's server construction.
