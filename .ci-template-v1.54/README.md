`ci.yml` and `nightly.yml` each have hard companions: copying a workflow
without the files listed as required gives you a job that cannot run — and,
in trivy's case, one that fails on a flag error with its real findings hidden
behind it (measured go-enclave 2026-08-26, ten HIGH CVEs).

The canonical CI workflow every project copies into
`.github/workflows/ci.yml`. It encodes
[conventions/devops.md](../../conventions/devops.md) §1 (one workflow, both
hosts, guarded divergence, the required gate job), §8 (the mandatory
security-analysis suite) and §9 (latest everything).

## Why copy-in, not `workflow_call`

Reusable workflows resolve from the *server the run executes on*. The
canonical copy lives in the handbook on the internal Gitea, which GitHub-side
runs cannot reach, so they could never fetch it. Every repo therefore carries its
own copy, stamped with the template version (`# ci-template: v1`), and
divergence outside the marked `CUSTOMIZE` blocks is a defect.

## Using it

1. Copy `ci.yml` and `nightly.yml` into the repo's `.github/workflows/`,
   **with their companions from the table above** — `actionlint.yaml` to
   `.github/`, `.trivyignore` and `.trivy-version` to the repo root, and
   `install-trivy.sh`, `in-toolchain-image.sh`, `assert-build-tags.sh` and
   `reap-stale-ci-stacks.sh` to `scripts/` (executable). From ci.yml v1.23,
   `revert-red-main.yml` goes beside `ci.yml`.
2. Resolve every `CUSTOMIZE` marker: coverage threshold, build tags, test
   host tuning and timeout, the soak length and target, the nightly hour,
   further stages and jobs (lint, build, unit and race on the PR tier, the
   rest on the full tier), CI Gate's needs and check lines, and
   `revert-red-main.yml`'s `REVERT_STEPS`.
3. The Makefile carries every flag set: CI runs `make lint`, `build`,
   `coverage`, `security`, `deps-check` and `integration-test` in the
   devcontainer image with the variables in
   [devcontainer.md](../../conventions/devcontainer.md) §6, so gosec excludes
   (each with a written justification) and nested-module builds live there
   (devops.md §4 — CI runs what a developer can run). From v1.23 it also
   carries `make it-image` and builds an image only when the daemon lacks its
   tag (ci-standard.md §9; go-qrdb #814 is the worked example).
4. On template updates, bump the `ci-template:` version here and in the
   file, and roll the change to every repo in one pass — the same
   portfolio-wide, never-piecemeal rule as toolchain bumps. CI template
   v1.21 rolls out after the P1 dev-complete dates, one PR per project
   behind its coordinator (owner, 2026-10-17, via the Tenant Agent m523
   item 32; open: which dates are the P1 dev-complete dates). v1.21's
   content goes through the Tenant Agent before any project adopts it
   (m598).
5. **Joining the Codex review pool** (`code-review.yml`, Tenant Agent
   m2289 item 2, ruling 399). In the same step that admits the repository
   to the codex runner and installs the codex-review App on it, its
   repository Actions variable `CODEX_REVIEWER` is set to the App's bot
   login. Unset, the codex job fails and does not default the reviewer
   (v5.9.1), so no PR in the repository can land. The variable is set, and
   `GET /repos/<owner>/<repo>/actions/variables/CODEX_REVIEWER` checked for
   200 before the repository's first `code-review` PR, by the Tenant Agent,
   never by a department (m2113). Infrastructure's App installation has no
   Actions-variables permission (both calls answer 403). go-frostdkg
   and six other pool repositories lacked it until 2026-11-09 11:56Z.
